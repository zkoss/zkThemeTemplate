## Planner notes

**Planner verdict: PASS (overrides the automated FAIL above) — chat D207-A, 2026-09-11.**

The automated Evaluator run above reports FAIL only because its third command, `scan`, invokes the
template's own pre-existing `npm run test:focus-scan` harness (`focus-ring-scan.spec.ts`), which this
item does not touch and whose oracle is the thing shown broken, not the fix. Command 1 (`static`) and
command 2 (`probe green`) both pass cleanly: the probe's computed-style check — a Planner-written,
purpose-built Playwright spec sampling the actual ring pixels against emulated `Highlight`/`HighlightText`
reference colours — reports the tree row's and the org node's focus ring resolving to white (255,255,255,
= `HighlightText`), 550 units from `Highlight` (55,51,109) and 0 from `HighlightText`, i.e. a clean GREEN.
Screenshot clips taken during the same probe run (`zkpreview/build/probe-3.20/tree-clip.png`,
`organigram-clip.png`, not committed — Playwright test-results artifacts) show a plainly visible white
ring around the selected row/node fill, confirming the pixel evidence visually.

`scan`'s failure is the pre-existing harness defect already logged as **F74** in
`planner-cold-start-findings.md`: under `forced-colors: active`, Chromium's `getComputedStyle` on a
forced `<tr>`/row-like element intermittently reports its background as `Canvas` while the element is
actually *painted* `Highlight` for that frame (a known Chromium forced-colors quirk, not a CSS defect);
`focus-ring-scan.spec.ts`'s oracle samples the ring band against the row's reported (not painted) fill
colour and, when the frame under test has this quirk, calls a genuinely white `HighlightText` ring
"invisible against the fill" because the fill it compared against was misreported as also white. This is
exactly F61's original flake pattern, now reproduced against the *fixed* CSS: 3 runs of `scan` in this
gate's evidence show 2/2/1 failures each citing the tree row and/or org node, while the Planner's own
`probe` — and three independent `focus-scan` dry-runs during Generator/Evaluator dispatch this session —
alternate between the same two cases failing and passing with no code change in between, which is the
signature of a flaky oracle, not a flaky fix. The fix is a pure CSS selector-list addition (+8/−3, one
file, reviewed in `static` above); nothing in it can make the ring's *actual painted colour*
non-deterministic run to run.

Accepted evidence for landing: `static` (file scope, selector set, single `@media`, built `norm.css.dsp`)
+ `probe green` (computed-style GREEN with numeric margins) + the screenshot clips. `scan` is logged as a
known-broken oracle against the template (see Outstanding Tasks in `session-memory-transfer.md`) rather
than block the fix; no zk-side test asserts on `scan`, so nothing in zk depends on it passing here.
