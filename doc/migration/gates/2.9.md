## Design notes (Opus, non-binding)

Read: B110_ZK_6112Test.java, B110-ZK-6112.zul, StandardThemeProvider.java (insertResetURI / getThemeURIs).

Soundness — every assertion does follow from the provider, none contradicts it. insertResetURI picks reset.css vs reset-embed.css purely on Library.getProperty("org.zkoss.zul.theme.browserDefault", "false"), so testResetPrecedesWcs (reset.css present, reset-embed.css absent) and testBrowserDefaultServesEmbedReset (the mirror image) are exactly the two branches of that ternary. The substring probes are non-overlapping: "/zul/css/reset.css" cannot match a reset-embed href and vice versa, so the two assertFalse checks are not accidentally self-satisfying. Nothing is asserted that the provider does not promise; the "absence" assertions are marginally stronger than the provider's own contract (it only promises what it inserts, not that no other code links the other file), but no other inserter exists today.

Under-assertion, the main gap. The provider promises the reset sits *immediately* before the first "~./zul/css/zk.wcs" entry — it inserts at that exact index — while the test only checks reset < wcs. A regression that inserted the reset at list position 0 with other stylesheets in between would still pass, and position 0 is precisely the provider's fallback branch when no zk.wcs entry is found, so it is a live failure mode. Since all these hrefs come from the same uris list, DOM link order should mirror list order; asserting reset == wcs - 1 would cover the promise at no extra cost. The zero-index fallback path itself (no zk.wcs in the list) is untested, as is the ordering guarantee in getThemeURIs that insertResetURI runs *before* bypassURI — i.e. the reset URI never receives the non-default-theme suffix. A third case with a non-default theme set would pin that down.

Test-isolation smell. Library.setProperty mutates process-global state that the in-JVM server reads per render; the restore is setProperty(key, null) rather than save-and-restore of the previous value, and nothing serialises this against other tests sharing the JVM. It passes under -PmaxParallelForks=1, but a parallel run could see reset-embed leak into an unrelated page. Worth a comment on the test, or a fixture that captures and restores the prior value.

Cosmetic / drift. assertFalse(indexOf(...) >= 0) reads awkwardly; assertEquals(-1, indexOf(...)) gives a better failure message. The ZUL page's prose ends with "The button below must render in the Marble style (rounded corners, Marble palette)" — nothing in the test asserts any rendered style, so the page text promises a visual check the automation does not perform; either drop that sentence or leave it explicitly flagged as manual.
