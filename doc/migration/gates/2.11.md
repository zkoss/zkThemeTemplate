## Design notes (Opus, non-binding)

Rule coverage — complete, one-to-one. Every LESS rule survives: the shared fill (background + z-skeleton-pulse 1.5s ease-in-out infinite) on .z-skeleton-active and .z-skeleton-overlay; the three shapes; position/overflow on .z-skeleton-active; `.z-skeleton-active *{visibility:hidden!important}`; ::after with content:''!important + inset:0 + background; ::before{content:none!important}; .z-skeleton-masked{visibility:hidden!important}; the keyframes; and the prefers-reduced-motion override. The LESS mixins `.z-skeleton-fill()`/`.z-skeleton-shape()` compiled to exactly the selectors the CSS now writes out longhand (.z-skeleton-active.z-skeleton-rect etc.), so specificity is unchanged. The only ordering change is cosmetic: the shape block now precedes the .z-skeleton-active base block (in LESS the shape mixin was applied last, nested). No property is declared in both, so cascade outcome is identical. All five --zk-skeleton-* override hooks are preserved with the same names and the same literal fallbacks for duration, text radius and min opacity. The file is wrapped in `@layer zk-components {`, matching the convention in zkmax's own CSS sources (e.g. zkmax/.../wgt/css/drawer.css line 10) — consistent, and it does lower the rules beneath any unlayered app CSS, which is the intended Marble behaviour rather than a regression.

Token mapping — both readings are defensible; one is exact, one is a deliberate hue shift. @baseBorderRadius resolved to var(--zk-base-border-radius) = 4px in the retired profiles (_default.less/_compact.less line 30); --zk-shape-corner-extra-small is 4px (_shape.css line 5) and is the token Marble already uses for buttons, inputs, dialogs, menus — an exact numeric and semantic match, no comment needed. @colorGreyLighter resolved to var(--zk-color-grey-lighter) = #F2F2F2, annotated "Field disabled Bg"; the port picks --zk-color-surface-variant = #f0f4fa, i.e. a slightly blue-tinted low-emphasis surface rather than a neutral grey. That is the right semantic tier (a placeholder is a surface, not a disabled field) and it matches --zk-color-surface-container exactly, so the choice between those two is a coin flip; surface-variant is the better name for the intent. Worth flagging to the Planner: neither the old nor the new token has a dark-mode redefinition in the shipped token files (no prefers-color-scheme block anywhere under zul/css/tokens/), so the original LESS comment's promise that the placeholder "follows dark mode" is still unfulfilled — carried over as-is, not introduced here.

zk script insertions — in scope, with one naming nit. build-css.js adds a single member, 'skeleton.css.dsp', to CSS_URI_BACKED plus two comment lines, so the orphan guard stops treating the file as unreferenced. check-css-dsp.js adds an 8-line block that scans the language-level `remainder` for `<stylesheet href="…css.dsp">` and pushes each as a requirement labelled "(global <stylesheet>)". Nothing else in scripts/ changed, and neither edit touches component-level handling — exactly the two behaviours row 2.11 names. Nits, none blocking: (a) the new entry now lives in a set literally named CSS_URI_BACKED while its own comment says the file is *not* css-uri backed — either rename the set or split out a GLOBAL_STYLESHEET_BACKED list before more such entries accumulate; (b) the href regex requires double quotes and won't match single-quoted attributes or an href written after other attributes on a multi-line tag — fine for ZK's own lang-addon.xml files today, brittle if third-party addons are ever scanned.
