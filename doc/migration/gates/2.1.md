## Design notes (Opus, non-binding)

Both stages green; the notes below are advisory only.

WHAT WOULD SURPRISE A ZK MAINTAINER

1. Recursive composite. Root zk/settings.gradle now does `includeBuild new File(rootDir, "zkpreview")` while zkpreview/settings.gradle does `includeBuild("../../zk")` — i.e. zkpreview includes the very build that includes it. It configures (the static stage proves it), and zktest is the precedent, so this is consistent rather than novel; still worth one line in the migration doc so nobody "fixes" it. Note the new include sits inside the `user.name != "zkoss"` guard, so zkpreview is invisible to the zkoss CI account — a compile break in zkpreview will not surface in CI, only for local developers.

2. EE coupling is hard, not optional. build.gradle declares `zkex` and `zkmax` unconditionally, but the zkcml substitution block in zkpreview/settings.gradle is guarded by `resolveProjectDir("../../zkcml") != null`. On a CE-only checkout the guard degrades quietly at configuration time and then resolution fails hard, since `org.zkoss.zk:zkex:11.0.0-SNAPSHOT` will not be in mavenLocal/mavensync. If a CE-only developer must be able to run the preview, the zkex/zkmax dependencies need the same conditional as their substitutions; if not, say so explicitly ("zkpreview requires a sibling zkcml checkout") rather than leaving the settings-level graceful skip implying otherwise. Also, `zuti`/`za11y` are substituted but never declared (fine, they arrive transitively), and `zkwebfragment` is both substituted in settings and globally excluded in build.gradle — dead weight that reads as a contradiction.

3. Port 8085 is fine. It is overridable via `-PhttpPort`, avoids zksandbox/zktest on 8080, and the live stage checks the port free both before and after — good hygiene. Item 2.3 should read the port from one place rather than hardcode it in the Playwright config too.

4. Playwright baseURL (2.3): the context path is `/zkpreview`, and the probe used `http://127.0.0.1:8085/zkpreview/smoke.zul` (127.0.0.1, not localhost — keep that, it dodges the IPv6/::1 first-resolution stall on macOS). baseURL should therefore be `http://127.0.0.1:8085/zkpreview/` with the trailing slash, so page paths stay relative and 2.2's directory structure under src/main/webapp maps 1:1 onto URL paths. That works cleanly for 159 pages — no per-page registration (no config.properties equivalent, no *.zul allowlist), which is the main advantage of this layout over hosting the pages in zktest.

5. The lost-query-string redirect (appendix A.5) is live here, and web.xml makes it easier to hit: `<welcome-file>smoke.zul</welcome-file>` means any request to a directory (`/zkpreview/`, or `/zkpreview/<subdir>/` once 2.2 lands) goes through the container/servlet redirect that drops the query. Marble preview pages are exactly the pages likely to be driven by query params (theme, device type, variant). Recommendation for 2.3: make every navigation target an explicit `*.zul` path so the redirect is never in the path, and add one negative test that a URL with a query survives — otherwise the failure mode is a silently-default-rendered page and a green screenshot baseline.

6. Live output: one thing to look at before baselining. `zkmax/css/tablet.css.dsp` is in the served HTML but is absent from the browser's `document.styleSheets` list, while reset.css, zk.wcs and zkex skeleton.css.dsp all appear. Either that DSP sheet did not return parseable CSS (wrong content type or a DSP error page still served 200) or the headless run resolved to a different device profile than the curl run. Since "tablet CSS works" is a stated reason for pulling zkmax in, a sheet that is linked but not applied is precisely the kind of thing that would pass 2.1 and then poison 2.2/2.3 screenshots. Worth a direct GET of that URL to confirm it is real CSS.

7. Other live-output observations, all minor: every resource URL carries a `;jsessionid=...` path parameter (URL-rewriting session tracking on first request), so 2.3 must not assert on stylesheet URLs verbatim or use them as cache keys. `title` comes back empty because smoke.zul sets only the window title and no `<?page title=?>` — do not identify pages by document title in 2.3. `670 --zk-*` declarations is a plausible Marble token count for one page, but as written it is a smoke number; if it is meant to catch token regressions, pin an expected range rather than "> 0". The `skeleton.css.dsp` still being a .dsp is expected (EE has not moved off DSP) but is a useful reminder that the LESS/DSP-deprecation decision only covered CE CSS.

8. Divergence from zktest that will matter in 2.2. The static stage asserts web.xml contains "nothing from zktest" — a deliberately minimal descriptor with no `zk.xml`, no session-config, no library properties. Any of the 159 pages that today rely on zktest's zk.xml (theme/device defaults, timeout, error pages, `org.zkoss.zk.ui.*` library properties) will render differently under zkpreview without erroring. Auditing zktest's WEB-INF for properties the moved pages depend on is the single highest-value prep step for 2.2.

9. Not wired into quality gates: no checkstyle, no test task, no lint in zkpreview/build.gradle, and `providedCompile javax.servlet:servlet-api:2.4` against a `version="3.0"` web.xml (inherited from zksandbox — compiles today, but will bite if ZKPreviewServlet ever touches a 3.0+ API). Acceptable for a preview host; just intentional rather than accidental.
