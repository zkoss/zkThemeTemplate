## Design notes (Opus, non-binding)

Statuses and oracle. Every one of the 183 rows carries a status the plan allows: 182 IDENTICAL and one IDENTICAL-ON-RESHOOT 1 (avatar-gallery.png). Zero OPEN, zero FIXED, zero NOISY, and noisy-exceptions.tsv holds no active row at all — every line is a comment, including the two delistings (avatar-gallery, component-theming-gallery) whose evidence is preserved as commentary. So the "NOISY only with evidence" rule cannot be violated today: there is nothing to evidence. All three ledgers do name the same oracle, 40c4ddda. They do NOT name the same zkpreview tree: 2.6-gallery.tsv pins zk 79ce20577a while 2.7-state.tsv and 2.8-tablet.tsv pin 49a7ebe65c. Stage 4 checks only the oracle side, so nothing in the gate notices that the gallery family was measured against a different zk commit from the other two. Stage 6 covers the tablet family against the final tree; the gallery and state families remain measured at their own, older, zkpreview commits and no stage re-measures them. If the Planner wants "the whole 183 measured against one tree" to be a claim P2 can make, that is a third re-measure, not a bookkeeping change.

The one status a future reader can misread. It is not IDENTICAL-ON-RESHOOT — it is plain IDENTICAL. The single recorded reshoot row, avatar-gallery, is honest and if anything under-states its history: it was on the evidenced exception list, delisted 2026-09-11 on a 3/3 clean sample, and then flaked again in both the 2.6 Generator and Evaluator runs. The delisting rationale reads stronger in the file than the runs since have supported. The larger problem is the inverse. Gate 2.6's own Evaluator run needed reshoots for grid-header, listbox-header and splitter, all recorded as plain IDENTICAL; gate 2.7's needed one for bandbox-focus, recorded as plain IDENTICAL; and my stage-6 run just now saw 1 of 30 tablet shots differ on round 1 and match after one reshoot, while 2.8-tablet.tsv records 30 IDENTICAL and all three prior runs saw 30/30 at the first shot. All three families have now shown a first-shot flake that their ledger does not carry. The Planner has already ruled (2.7 notes) that the second column describes one run's luck rather than a property of the page, and that ruling is right, but the file does not say so: a reader with only the TSV in hand reads IDENTICAL as "deterministic" and IDENTICAL-ON-RESHOOT as "known flaky", and both readings are wrong. One header line per ledger stating that the status records the capture run, not a stable attribute, would close this at no cost and is cheaper than the third column already parked in P4.

Tooling note on stage 6 itself. verify-2.8.sh live prints the flaky shot names and the "flaky rows whose re-shoot count differs from the ledger's" informational block; the gate-p2.sh stage-6 wrapper does not — my output gives "DIFF 1" and "1 now identical" with no name. So the P2 gate's own final re-measure detects a flake and then discards the only fact that would let anyone act on it. Worth surfacing the name.

F62 and P4 (gates 2.9, 2.11). The regression itself is closed and closed at the right level: the Marble skeleton.css is a 1:1 port of the retired LESS (Opus verified rule-by-rule), the orphan guard learned the file, and check-css-dsp.js now verifies global <stylesheet href=...css.dsp> entries — which is the class fix, so no second dangling global stylesheet can hide the way this one did. The negative check was exercised, not merely asserted. What is left for P4 is trailings rather than the regression: (1) the new href scan requires double quotes and an href in a predictable position, fine for ZK's own lang-addon.xml, brittle if third-party addons are ever scanned, and the live proof covered --module zkex only — nothing shown says the global check runs for every module in CI; (2) skeleton.css.dsp now sits in a set named CSS_URI_BACKED while being global-stylesheet-backed, a rename or split before more entries accumulate; (3) the token carry-over — neither --zk-color-surface-variant nor its LESS predecessor has a prefers-color-scheme redefinition anywhere under zul/css/tokens/, so the source comment's "follows dark mode" promise is still unfulfilled; that one is a real user-visible gap in P4 scope, not housekeeping, and if it is not going to be fulfilled the comment should be deleted rather than carried. From 2.9: the recorded P4 item is the assertion tightening (reset == wcs - 1 rather than reset < wcs; the index-0 fallback branch untested; the insertReset-before-bypassURI ordering untested). Two smaller things from 2.9 do not appear to be recorded anywhere as P4 and probably should be — the test restores org.zkoss.zul.theme.browserDefault with setProperty(key, null) instead of save-and-restore of the prior value, which is safe only under -PmaxParallelForks=1, and B110-ZK-6112.zul's closing sentence promises "the button below must render in the Marble style" while no assertion checks any rendered style, so the page advertises a visual check the automation does not perform.
