# ZK 10.2.1 → 10.3.0.1 — DOM-Change Report (Phase 2)

**Scope:** Does any ZK-generated markup / CSS-class change between `10.2.1-jakarta` and
`10.3.0.1-jakarta` break Marble's `.z-*` selectors?

**Method:** CaseFoundry `suggest_migration('10.2.1','10.3.0.1')` (release-notes level) →
verified against `git diff v10.2.1..v10.3.0.1` on `/Users/hawk/Documents/workspace/ZK10/zk/zul`.

**Verdict: no breaking DOM change.** One DOM reorder (tabbox) exists but is provably safe for
Marble. No action required in this phase.

---

## 1. CaseFoundry release-notes level

`suggest_migration('10.2.1','10.3.0.1')` returned only:
- OSGi headers added to all ZK jars.
- CVE dependency bumps: jython 2.7.4, rhino 1.8.1, commons-lang → commons-lang3 3.20.0, pdfjs 4.10.38.
- **1 behavioral change:** Combobutton now fires `onOpen` on `setOpen(boolean)` (aligns with Menu).

None are DOM/CSS-structural. The Combobutton `onOpen` change is **app-behavioral only** (event
timing) — no markup or class change — so it has **no theme impact**.

## 2. Source diff — generated markup

`git diff v10.2.1..v10.3.0.1` on `zk/zul` touched **2 mold files** and **13 `.ts` files** with
any markup relevance.

### 2a. Mold files (the redraw templates that emit HTML)

| File | Change | Theme impact |
|------|--------|--------------|
| `menu/mold/menu.js` | `href="javascript:;"` → `href="javascript:void(0);"` on the menuitem `<a>` | **None** — `href` value is not a Marble selector target; class list unchanged |
| `tab/mold/tabbox.js` | Scroll-arrow divs (`z-tabbox-left-scroll` / `z-tabbox-right-scroll`) and the tabbox toolbar moved to render *inside* the top/bottom orientation branches instead of after tabs/tabpanels | **Sibling-order change only; class names unchanged.** Verified safe — see §3 |

### 2b. `.ts` files (client widget logic)

All 13 changed `.ts` files — `inp/ComboWidget`, `inp/Combobox`, `inp/Slider`, `inp/Textbox`,
`layout/Borderlayout`, `menu/Menuitem`, `menu/Menupopup`, `mesh/HeaderWidget`, `mesh/MeshWidget`,
`sel/SelectWidget`, `wgt/A`, `wgt/Checkbox`, `wgt/Combobutton` — were grepped for any
class/DOM-structure mutation (`$s(`, `addClass`, `removeClass`, `class=`, `setAttr`, `zcls`,
`innerHTML`, `redraw`, `domAttrs`).

**Result: zero class or DOM-structure changes.** The edits are logic and event handling only
(scroll behavior, event dispatch, keyboard nav). No Marble selector is affected.

## 3. Tabbox DOM reorder — order-sensitivity analysis

The one structural change (tabbox scroll arrows + toolbar reordered among siblings) was
cross-referenced against Marble's tabbox CSS
(`src/main/resources/web/js/zul/tab/css/tabbox.css`):

- Scroll arrows are positioned with `position: absolute` and explicit `left`/`right`/`top`
  anchored to the `.z-tabbox` root (`.z-tabbox` is `position: relative`, line 32; arrow rules
  lines 248–265).
- The tabs toolbar (`.z-tabbox > .z-toolbar.z-toolbar-tabs`) is likewise `position: absolute;
  top: 0; right: 0` off the root (lines 317–323).
- **No** adjacent-sibling (`+`) or general-sibling (`~`) combinators, **no** `:first-child` /
  `:last-child` / `nth-child()`, and **no** `order:` on the arrows or toolbar.

Because every affected element is positioned absolutely against the root rather than relative to
its DOM neighbours, changing their sibling order has **zero visual effect** in Marble.

## Conclusion

No selector breakage from the version bump. The Combobutton `onOpen` behavioral change is noted
for application authors but requires no theme change. Proceed to CSS bug-fix triage
(`doc/zk-10.3-css-bugfix-triage.md`); verify the tabbox reorder visually in Phase 4 as a
belt-and-braces check.
