Orchestrator Playbook — 流程圖與概要

ZK-Material 主題驗證 Harness 的整體運作架構，由主 Claude session 作為 Orchestrator 協調 Spec-Author、Evaluator 與 Generator 三類 Agent。

Orchestrator 動作 Subagent 使用者介入 檔案產出 判斷分支

二、涉及的 Agent

Agent 角色 並行性 負責的工作
Orchestrator
（主 Claude session）		 協調者 單一 讀 status file、決定 batch、dispatch agent、合併結果、處理 token/library 升級、決定是否停止迴圈
zk-spec-author 規格作者 每元件呼叫 1 次 讀 ZK JS 源碼，產出元件結構事實、主題契約、HTML mockup、iceblue baseline。在 ralph-loop 開始前執行
zk-theme-evaluator 檢驗者（read-only） 最多 4 並行 用 Chrome 量測 computed CSS、比對 contract 期望值、寫 eval report、更新 status row。不可以編輯 CSS
zk-theme-generator 實作者（write） 嚴格序列（1 次 1 個） 依 eval report 修 CSS → 跑 npm run build:css → 寫 gen report。不可以瀏覽或量測

三、涉及的 Skills

Skill 用途
zk-component-rules ZK 元件的結構性事實（DOM、state classes、CSS 檔案 bundling、quirks）— 與主題無關。Spec-Author 與 Evaluator 都會讀取，做為驗證 ZK 行為的依據
zk-consultant / zk-technical-writer 輔助技能：ZK 框架知識諮詢與文件撰寫（不直接參與 main loop）

四、Plan / 文件結構

檔案 寫入者 內容
doc/orchestrator-playbook.md 人 主流程指南（這份）— Orchestrator 的操作說明書
doc/harness-plan.md 人 Harness 整體架構說明（companion doc）
tasks/work-status.md Orchestrator + Evaluator 狀態真實來源。每元件一行，紀錄當前 status（PENDING、NEEDS_FIX、FIXING、RE_EVAL_NEEDED、VERIFIED、ESCALATED_TOKEN_FIX、STALLED…）

tasks/escalation.md Orchestrator STALLED / OSCILLATING 元件的失敗歷史，需使用者介入
tasks/skill-gaps.md Evaluator JS source 漂移紀錄（js-drift），觸發重新呼叫 spec-author

doc/contracts/baselines/<comp>-iceblue.png Spec-Author iceblue 主題的參考截圖（核可比對基準）

五、Status 狀態機

PENDING FIXING RE_EVAL_NEEDED NEEDS_FIX VERIFIED ✓ ESCALATED_TOKEN_FIX ESCALATED_LIBRARY_CONFIG STALLED OSCILLATING BLOCKED EVALUATING_BLOCKED

終態（迴圈停止條件）：VERIFIED、STALLED、OSCILLATING、CONSTRAINT、ESCALATED_TOKEN_FIX。

六、關鍵並行/序列規則

階段 並行度 原因
Evaluator 最多 4 並行 每個 Evaluator 用獨立 Chrome tab；eval report 一檔一元件無 race；status file 的小 race 可恢復
Generator 嚴格序列 1 npm run build:css 寫入 target/ 是 non-atomic；並行 build 會互相覆蓋
Eval + Gen 同一輪 可 Evaluator 只讀 CSS；Generator 寫 CSS。若針對不同元件則不衝突

七、停止條件（Orchestrator 主動停下並回報使用者）

  1. 所有 row 都進入終態
  2. tasks/escalation.md 有新項目
  3. Generator build 失敗
  4. Preview app 死掉（任一 EVALUATING_BLOCKED）
  5. 使用者輸入 /stop 或中斷
  6. 連續 5 個以上元件 verified 完成 — 建議與使用者 checkpoint
  7. ≥ 3 個元件被同一個 token 阻擋（可能是真實規格問題）
核心設計概念：把「實作（Generator）」和「驗證（Evaluator）」徹底分離，並讓「規格（Spec-Author）」先於兩者產出契約。使用者只需審核契約一次，後續迴圈就能自動跑到 VERIFIED 或升級到需人工介入的狀態。
使用者必須親自做的事：
  • 啟動 Preview App（withjdk.sh 17 mvn test exec:java@preview-app）
  • 審核每個元件的 contract → 翻轉 contract-approved: true
  • 處理 tasks/token-issues.md 裡的 token 修正（影響整個 theme）
  • 處理 tasks/library-config-issues.md 的 widget 程式碼修改
  • 處理 tasks/escalation.md 的 STALLED / OSCILLATING 元件
