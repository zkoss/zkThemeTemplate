# L-2 瀏覽器支援聲明 —— 利弊分析(2026-08-07)

> ## ✅ 已拍板(2026-08-07):**選項 C —— 保守**
>
> **不對 Safari 做任何版本下限聲明;`-webkit-` 285 條真前綴全數保留,
> 只移除 `-moz-` / `-ms-` / `-o-` / `-khtml-`。**
>
> 決策紀錄已寫進 [L3-F](../doc/iceblue-drop-less-plan-appendix.md);
> P4a 上限 **945 → 788**、P4b **143 → 15**,拍板後的完整分解見 **§10**。
> 以下 §1–§9 是拍板當時的分析原文,**不改寫**。

---

## 1. 這個決定實際上在決定什麼

**不是**「IceBlue 支援哪些瀏覽器」這句話本身,而是:

> 輸出端 **1132 條 vendor prefix 宣告**裡,**哪幾條可以刪**。

刪掉的量決定 P4a / P4b 的 G-delta 上限;刪錯的那幾條會變成**只在特定 OS + 瀏覽器組合上**
才看得到的視覺回歸。

---

## 2. 為什麼這一個決定比其他決定重

整個棄用 LESS 計畫的每一階都有機械證據兜底 —— P3/P5/P6 是 `files differing: 0`,
P4a 有形狀檢查(diff 只允許 `- <prefixed>`)。**但形狀檢查證明的是「我們只刪了打算刪的」,
不是「刪掉是安全的」。**

計畫書自己寫了([execution-plan:152](../doc/iceblue-drop-less-execution-plan.md#L152)):
視覺 A/B 在 P4 **價值最低** —— 截圖是在一個瀏覽器跑的,答不出「這個前綴在我們宣告支援的
瀏覽器裡是不是死的」。

⇒ **P4 是全計畫唯一一個「安全性完全由一句政策聲明承擔」的階段。**
所以這句聲明必須是**明文可查、客戶可引用**的,不能是內部共識。

---

## 3. 一個容易被忽略的不對稱:棄用 LESS 改變了「不清理」的成本

| | LESS 時代 | 純 CSS 之後 |
|---|---|---|
| 前綴哪來的 | `.borderRadius()` 等 4 個 mixin **自動展開** | **來源檔裡的字面文字** |
| 維護成本 | **0** —— 改一次 mixin 定義,103 個呼叫點跟著變 | **每次加一個圓角都要手抄 5 行** |
| 漏抄的後果 | 不可能發生 | 前綴鏈不一致,而且沒有東西會檢查 |

**「留著前綴」在 2026-08 之後比在此之前貴得多。** 這不是「順便清理」,是**在為純 CSS 來源
決定往後的維護形狀**。反過來說,若決定保留,建議一併決定要不要引入 autoprefixer ——
但那等於把剛拆掉的編譯層再裝一個回去,會抵銷棄用 LESS 的一部分理由(見〈選項 C〉)。

## 4. 事實盤(全部來自 P0 輸出端實測,不是估算)

### 4.1 總量

| 前綴 | 條數 |
|---|---|
| `-webkit-` | 313 |
| `-moz-` | 283 |
| `-ms-` | 281 |
| `-o-` | 250 |
| `-khtml-` | 5 |
| **合計** | **1132** |

### 4.2 扣掉不可動的部分

| 群 | 條數 | 性質 |
|---|---|---|
| **B 群 carve-out** | **44** | **私有屬性,前綴就是它的正式名字**,從未標準化。刪掉 = 刪功能,**與 L-2 無關** |
| **A 群** | **945** | 真前綴,且**逐 rule 實測 945 條全部有無前綴同伴** ⇒ 純移除,零判斷(P4a) |
| **C 群** | **143** | 手寫的前綴宣告,**所有判斷都在這裡**;其中 **26 條無同伴**,須「移除 + 新增標準宣告」成對替換(P4b) |

**可移除上限 = 945 + 143 = 1088 條**,佔全樹 14863 條的 **7.3%**。

B 群 44 條明細(**任何選項下都不刪**):`-webkit-font-smoothing` 16、`-moz-osx-font-smoothing` 16、
`-webkit-touch-callout` 6、`-webkit-tap-highlight-color` 4、`-webkit-user-drag` 1、`-webkit-user-modify` 1。

### 4.3 真正對 L-2 敏感的只有一小撮

1088 條裡,**在任何合理下限之下都已經死透**的:

| 項目 | 為什麼死 |
|---|---|
| `-o-` **250** | Opera Presto,2013 年停止開發 |
| `-ms-` **281** | IE 專屬。IE 已 EOL,Edge(Chromium)不需要 |
| `-khtml-` **5** | Konqueror,2005 年前 |
| `-moz-`(扣掉 16 條 carve-out)**267** | `user-select` Firefox **69**(2019)、`appearance` Firefox **80**(2020)起無前綴 |
| 舊 flexbox `*-box-orient` 16 / `*-box-flex` 12、`*-transition-*` 28 | 2009 舊規格 / 早已無前綴 |

**⇒ 約 800 條與 L-2 無關,怎麼訂都可以刪。**

**真正由 L-2 決定的,只有 `-webkit-` 這一側,而它又只綁一個變數:Safari 下限。**

| 屬性 | Safari 何時支援無前綴 | 條數 | 移除後在更舊 Safari 上的失效模式 | 嚴重度 |
|---|---|---|---|---|
| `appearance` | **15.4**(2022-03) | `-webkit-appearance` 13 | `input`/`select` **回到原生外觀** —— 版面明顯壞掉 | **高** |
| `backface-visibility` | **15.4**(2022-03) | 6 | 3D 變換時背面閃現 | 中 |
| `user-select` | **17.4**(2024-03) | `-webkit-user-select` 11 | 本來不該被選取的文字**變得可以選取**(拖曳把手、tab 標籤) | **低** |

> **資料來源標註(拍板前請覆核)**:`user-select` 的 Safari **17.4** 與 Firefox **69**、
> `appearance` 的 Firefox **80** 出自計畫書
> [plan-appendix:1142](../doc/iceblue-drop-less-plan-appendix.md#L1142) 與〈`.userSelectNone()`〉表,
> 已在本專案內查證過。**`appearance` 與 `backface-visibility` 的 Safari 15.4 是本文引入的新事實,
> 尚未在本專案內查證** —— 而 §5 的建議直接建立在這條線上,**請對 caniuse 覆核後再拍板**。

## 5. 分歧點只有一個:Safari 下限訂在 15.4 還是 17.4

這是本分析最重要的一段。

| 下限 | 可移除 | 換來什麼 |
|---|---|---|
| **Safari ≥ 15.4**(2022-03) | **≈ 1069 / 1088 = 98.3%** | 保留 `-webkit-user-select` 一族(11 條;另 8 條無同伴者兩種寫法都要留,故實際保留量 11–19) |
| **Safari ≥ 17.4**(2024-03) | **1088 / 1088 = 100%** | —— |

> **把下限從 15.4 拉到 17.4,只多清 11–19 條(1.7%),卻多排除了整整兩年份的 Safari 使用者。
> 投報率極差。**

而且被排除的不是「不想升級的人」:**macOS 上 Safari 大版本綁 OS 版本**,鎖在舊 macOS 的
企業客戶**沒有辦法單獨升 Safari**。iOS 同理。這是這個決定唯一真正的商業風險點。

另一邊,15.4 這條線擋掉的正是**高嚴重度**那一項(`appearance` 回歸會讓表單控制項外觀爆掉);
17.4 多買到的只是一個**低嚴重度、純互動、事後可補**的小瑕疵(文字可被選取)。

## 6. 三個選項

### 【A】Safari ≥ 15.4 · Chrome/Edge ≥ 100 · Firefox ≥ 100(≈ 2022 春)**【建議】**

- **可移除 ≈ 1069 條(98.3%)**,保留 `-webkit-user-select` 一族。
- P4a 945 條照原計畫**一顆機械化 commit**,形狀檢查不變。
- P4b 從 143 條降到 ≈ 124 條逐條判斷。
- **代價**:來源裡永久留著 11–19 條 `-webkit-user-select`(需在來源加註「Safari < 17.4」,
  否則下一個人會當成漏刪的死碼再刪一次)。

### 【B】Safari ≥ 17.4 · 常青「最近 2 個版本」(對齊 Marble)

- **可移除 1088 條(100%)**,來源最乾淨,不留任何需要註解說明的例外。
- **代價**:① 只多拿 1.7%;② 排除 2022-03 ~ 2024-03 之間的 Safari;
  ③ **常青聲明對企業客戶不是可稽核的承諾** —— 它會隨時間自動變嚴,而客戶簽的是白紙黑字。
  若採此案,建議寫成**固定版號**而不是「最近 2 版」。
- **不對稱風險**:IceBlue 是**既有**預設主題,ZK 10 → 11 升級的客戶會原地繼承它。
  對它提高下限 = **對既有客戶的 breaking change**;Marble 是全新主題,宣告什麼都沒有存量包袱。
  兩者用同一句聲明**在商業上並不對稱**。

### 【C】保守:只刪非 `-webkit-`,`-webkit-` 全數保留

- **可移除 ≈ 800 條**(`-ms-` 281 + `-o-` 250 + `-moz-` 267 + `-khtml-` 5,其中無同伴者仍須成對替換)。
- **好處**:對 Safari **不做任何聲明**,零回歸風險,而且仍拿到 74% 的清理量。
- **代價**:把 §3 的手抄成本永久留在純 CSS 來源(`-webkit-` 313 條裡有 285 條是真前綴)。
  要抵銷就得引入 autoprefixer ⇒ **把剛拆掉的編譯層裝回去**,抵銷部分棄用 LESS 的理由。
- **適用時機**:如果現在拿不到客戶端的實際瀏覽器分布,這是**唯一不需要那份資料就能安全執行**的選項。

---

## 7. 建議

**選【A】。** 三個理由:

1. **邊際效益已經在 15.4 這條線上耗盡** —— 再往上只剩 1.7%,而風險是雙倍年份的使用者。
2. **失效模式的嚴重度排序支持這條線** —— 15.4 擋掉高嚴重度的 `appearance`,
   17.4 只多買到低嚴重度的 `user-select`。
3. **可逆成本低** —— P4a 是純移除的單一 commit,真有客訴 `git revert` 就回到原狀。
   (**但不是零成本**:revert 後 P8 的 G-zero 核帳要重算 P4+P5+P7 的 delta 總和。)

## 8. 這個決定其實不該由主題單獨發明

**主題的瀏覽器下限不應該低於 ZK 11 本體的支援聲明,也沒有理由高於它。**
repo 內目前查不到任何既有的支援聲明(`grep` 全文,只有 Marble `CLAUDE.md` 的
「modern browsers only, last 2 versions」,那是**另一個主題**的)。

⇒ 若 ZK 11 本體的聲明已經存在,**L-2 直接引用它即可,不是一個獨立決策**。
⇒ 若本體還沒定,那 L-2 是被**產品決策**擋住,不是被工程擋住 ——
應該把它移到〈L2.5 交給 P8 的產品面問題〉那一類去推,而不是繼續掛在計畫裡等。

## 10. 拍板後的分解量測(2026-08-07)

**口徑**:直接 `require` `scripts/cssdiff.js` 的 `parse()` / `extractDsp()`,
所以每一條「宣告」與閘門那 **14863** 條是同一個定義。對象是 `baseline/` 的 85 個 `.css.dsp`。
「有無前綴同伴」= **同一個 rule context 內**存在去掉前綴後的同名屬性。

### 10.1 交叉確認:計畫書的 P4 數字全部重現

| 項目 | 計畫書 | 本次量測 |
|---|---|---|
| declaration 總數 | 14863 | **14863** ✓ |
| 前綴宣告 | 1132 | **1132** ✓ |
| B 群 carve-out | 44 | **44** ✓ |
| A 群 | 945 | **945** ✓ |
| A 群「無同伴」 | 0 | **0** ✓ |
| C 群 | 143 | **143** ✓ |

⇒ **P0 的稽核無誤**,新數字是在它之上再過一道「`-webkit-` 不動」的濾網,不是推翻它。

### 10.2 選項 C 的分解

| | 條數 | 處置 |
|---|---|---|
| A 群 non-`-webkit-`(`-moz-` 233 / `-ms-` 242 / `-o-` 233) | **708** | **P4a** 純移除 |
| C 群 non-`-webkit-`,有同伴 | **80** | **P4a** 純移除(形狀相同,併入) |
| C 群 non-`-webkit-`,**無**同伴 | **15** | **P4b** 逐條判斷 |
| A 群 `-webkit-` | 237 | 保留 |
| C 群 `-webkit-` | 48 | 保留 |
| B 群 carve-out | 44 | 保留 |
| **合計** | **1132** | 可移除 **803 = 73.8%** |

### 10.3 P4b 的 15 條(全部清單)

| 屬性 | 條數 | 處置 |
|---|---|---|
| `-moz-appearance` | 6 | **成對替換** → `+ appearance`(該 rule 只有前綴寫法) |
| `-ms-zoom` | 3 | **純移除** —— `zoom:1` 是 IE hasLayout hack,沒有要接手的標準宣告 |
| `-ms-touch-action` | 2 | **成對替換** → `+ touch-action` |
| `-moz-user-select` | 2 | **成對替換** → `+ user-select` |
| `-ms-flex-align` | 1 | 逐條判斷(2012 舊 flexbox,語意與 `align-items` 不完全等價) |
| `-khtml-user-select` | 1 | 逐條判斷(同 rule 是否已有 `-webkit-`/標準版) |

### 10.4 順帶揭出的一件事(已記為 S39)

計畫書〈A 類也不能直接移除〉寫「**合計 26 條**」無同伴 —— 那是 `user-select`(8)+
`appearance`(18)**兩個屬性的小計**,**全樹實際是 33 條**,另有 `-ms-zoom` 3、
`-ms-touch-action` 2、`-ms-flex-align` 1、`-webkit-text-size-adjust` 1。
原文不是算錯,是口徑窄;但**若照 A 群規則純移除,`-ms-touch-action` / `-ms-flex-align`
會刪掉沒有東西接手的功能** ⇒ P4b 的清單必須用 33 這個口徑去篩,不能用 26。
選 C 之後落在 P4b 範圍的是其中 15 條。

### 10.5 這次不做的事

- **不引入 autoprefixer** —— 見 §3 與 L3-F 的拍板理由。
- **不動任何 `.css` / `.less` 來源、不動 `baseline/`** —— 本次只有文件與量測,閘門未跑亦未變。
- 量測腳本是一次性的(scratchpad),**沒有進 repo** —— 若 P4a 開工時需要「移除前是哪 788 條」
  的可重跑清單,那時再產品化成 `scripts/` 下的檢查器比較合適(P4a 的閘門本來就要驗這件事)。
