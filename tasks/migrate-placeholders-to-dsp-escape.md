# 把內建 placeholder 機制遷移到公開的 `/*!dsp …*/` escape

> 建立於 2026-08-19。**尚未動工，本文件只是計畫。** 來源 CSS 一個字都沒改，
> `/*!dsp …*/` 在來源樹的出現次數目前是 **0**。
>
> **前提目前不成立（2026-08-19 更新）**：escape 機制曾在 2026-08-18 實作並驗證完成
> （18 條控制組 + 端到端，輸出逐 byte 未變），但已依指示**撤回**；`build-css.js` 現在只有內建的
> `PLACEHOLDERS` 表。所以本計畫多了一個 P-1 前置：**要先決定是否重新落地 escape 機制**，
> 之後 P0～P4 才有意義。機制本身的量測結論仍然有效，記在 `doc/dsp-in-source-tradeoff.md`。
>
> **開工前必須先拍板 §P0 的兩個問題** —— 其中一個會讓現行閘門 FAIL，不是風格問題。

---

# L1 執行摘要

## 核心目標

讓「內建的條件」與「使用者的條件」走同一條路。

現在有兩套機制做同一件事：內建的 `browserDefault` / `density` 條件走 `build-css.js` 裡一張固定的
placeholder 對照表（外加一份只允許兩個檔案使用的白名單），使用者的條件走新的 `/*!dsp …*/` escape。
兩套機制、兩種寫法、兩處要維護，而且使用者永遠只能用其中一套。遷移完成後對照表與白名單可以整批刪除，
theme 內建的條件就是「用公開機制寫出來的一個例子」—— 這對一個要成為 ZK 11 預設外觀的 theme 有額外
價值：內建機制自己會不會壞，跟使用者的機制是同一個問題，不再各自為政。

## 里程碑

| Phase | 內容 | 狀態 |
|---|---|---|
| **P-1** | 是否重新落地 escape 機制（2026-08-19 已撤回） | ⬜ 待拍板 |
| **P0** | 前置決策：分隔空白造成的閘門衝突、以及要不要補「定義一次、多處引用」的形式 | ⬜ 待拍板 |
| **P1** | 遷移 tablet 那組（範圍小，先試機制） | ⬜ |
| **P2** | 遷移 reset / norm 那組（範圍大，含整塊條件與 taglib header） | ⬜ |
| **P3** | 刪除 placeholder 對照表、白名單與相關守門 | ⬜ |
| **P4** | 文件與閘門收尾 | ⬜ |

## 現階段總體進度：**0%**

前置能力曾經完成，已撤回；遷移本身未開始。剩下的資產是量測結論與本計畫書。

## 一句話風險

遷移**不是**逐 byte 中性的：inline escape 會多留一個分隔空白，宣告層級的比對看不出差異，但
逐 byte 比對會出現現有分類無法解釋的差異，**現行閘門會直接 FAIL**。所以 P0 必須先在三個選項中選一個，
不能邊做邊看。細節與量測見 L3。

# L2 階段進度

## P0 — 前置決策（阻塞後續全部階段）

**目標**：把兩個會改變後續工作形狀的問題定案。

**輸入**：本文件 L3 的量測結果。
**輸出**：兩個決策，寫回本節。

### 決策 1：分隔空白與閘門的衝突

現行 placeholder 的 payload 自帶分隔（空白包在 EL 字串裡），inline escape 則是由 sentinel 自帶一個
空白。兩者語意相同、輸出不同：宣告層級的比對認定相等（closing tag 的 `>` 讓比對器把後面的空白視為
組合子空白而正規化掉），但逐 byte 比對會多出差異，且**不屬於現有任何一個已核可的序列化分類**，
於是逐 byte 檢查判定 FAIL。

| 選項 | 作法 | 代價 |
|---|---|---|
| **A** | 給 escape 補一個「不加分隔」的形式 | escape 機制多一個關鍵字（公開 API 變大）；閘門維持逐 byte 零差異 |
| **B** | 接受差異，新增一個已核可的序列化分類 | 閘門從「零差異」降級為「差異已分類」，與 P4a/P4b 的既有作法一致；但這次的差異是**我們自己造成的**，不是上游工具差異 |
| **C** | 不遷移 | 兩套機制長期並存 |

### 決策 2：要不要補「定義一次、多處引用」

同一段 `browserDefault` 條件在來源樹出現 **114 次**（見 L3 清單）。先前已拍板「不提供 define／引用
形式」，那個決策是針對**使用者**的使用情境。若同樣套用在遷移上，就是 114 份重複 payload。

| 選項 | 作法 | 代價 |
|---|---|---|
| **A** | 補 define／引用形式，再遷移 | 公開 API 變大；但 114 處變成 1 份定義 + 114 個短引用 |
| **B** | 不補，就地寫完整 payload | 來源檔會顯著變長且高度重複；任何一次條件字串調整要改 114 處 |
| **C** | 不遷移 | 同決策 1 的選項 C |

**驗收標準**：兩個決策都有結論並寫回本節；若任一決策選 C，本計畫結案為「不執行」。

## P1 — 遷移 tablet 那組

**目標**：先在小範圍上證明機制可用，再碰大的。

**輸入**：2 個來源檔（tablet 主檔與其 compact partial）的前綴，共 24 次。
**輸出**：同 2 個來源檔改用 escape；`PLACEHOLDERS` 表暫不動（P3 才刪）。

**驗收標準**
1. 宣告層級比對：0 differences。
2. 逐 byte 比對：依 P0 決策 1 的結論，或維持零差異（選 A），或落在新核可的分類內（選 B）。
3. 平板輸出的 density 兩份完整表都仍在，且 compact 只在 compact 生效 —— 用既有的 density 檢查驗。

---

## P2 — 遷移 reset / norm 那組

**目標**：完成剩下的來源檔，含兩種比前綴更麻煩的形式。

**輸入**：3 個來源檔 —— reset partial、norm 主檔、density token partial。含 90 次前綴、
4 對整塊條件、1 個 taglib header 標記。

**輸出**：三個檔案改用 escape。

**已知的三個麻煩處**（詳見 L3）
1. **整塊條件**：`<c:if>` 包住整段規則，用 statement 形式表達，位置與現行標記相同。
2. **taglib header**：目前是一個「請把 header 放在這裡」的標記，不是 DSP payload；改成 escape 之後，
   建置端判斷「這個檔案自己放 header」的邏輯要跟著改，否則會變成前置兩份或一份都沒有。
3. **partial 的許可**：帶 placeholder 的 partial 是靠它的進入點檔案拿到白名單許可的。escape 沒有
   白名單，所以這一層限制會自然消失 —— 這是 P3 能整批刪除白名單的原因。

**驗收標準**：同 P1 的三條，外加 header 位置不變（它不在檔首，而是在 token 與 reset 的接縫上）。

---

## P3 — 刪除對照表、白名單與相關守門

**目標**：讓遷移真正產生收益 —— 少一套機制，而不是多一套。

**輸入**：P1 / P2 完成後，來源樹中 placeholder 的出現次數為 0。
**輸出**：`PLACEHOLDERS` 對照表、`PLACEHOLDER_SOURCES` 白名單、以及只服務它們的那個還原方向守門，
全部刪除。

**驗收標準**
1. 全樹 placeholder 出現次數為 0（用檢查腳本斷言，不靠肉眼）。
2. 宣告層級與逐 byte 比對維持 P1 / P2 的結論。
3. escape 的既有控制組全綠 —— 刪東西不能把它們一起弄鬆。

---

## P4 — 文件與閘門收尾

**目標**：把「只有一套機制」這件事寫進文件，並讓閘門守住它。

**輸出**
1. `readme.md` 的〈write your own DSP〉補一句：theme 內建的條件本身就是用這個機制寫的。
2. 既有的 `browserDefault` 決策文件更新為「以 escape 表達」。
3. 閘門新增一條：來源樹不得再出現 placeholder 字串（防止回頭長出第二套機制）。

**驗收標準**：完整閘門 exit 0；文件連結檢查通過。

# L3 技術附錄

## A. Placeholder 清單（2026-08-19 實測，遷移範圍的完整定義）

**前綴形式（`.ZKBD `，選擇器位置）—— 合計 114 次**

| 來源檔 | 次數 | 編進哪個輸出 |
|---|---|---|
| `zul/css/base/_reset.css` | 56 | `zul/css/norm.css.dsp` |
| `zul/css/norm.css` | 34 | 同上 |
| `zkmax/css/tablet.css` | 14 | `zkmax/css/tablet.css.dsp` |
| `zkmax/css/_tablet-compact.css` | 10 | 同上 |

對帳：56 + 34 = 90，等於 `norm.css.dsp` 裡 `not empty …browserDefault` 的出現次數；
14 + 10 = 24，等於 `tablet.css.dsp` 的數量。

**整塊形式與標記**

| 標記 | 來源檔 | 對數 |
|---|---|---|
| `ZKBD-OFF-*` | `zul/css/norm.css` | 2 |
| `ZKBD-OFF-*` | `zul/css/base/_reset.css` | 1 |
| `ZKDENSITY-DEFAULT-*` | `zkmax/css/tablet.css` | 1 |
| `ZKDENSITY-COMPACT-*` | `zkmax/css/tablet.css` | 1 |
| `ZKDENSITY-COMPACT-*` | `zul/css/tokens/_density-compact.css` | 1 |
| `ZK-TAGLIB-HEADER` | `zul/css/norm.css` | 1 |

帶 placeholder 的來源檔共 **5 個**（前綴 4 個 + density token partial）。
`norm.css` 對 `ZK-TAGLIB-HEADER` 有 2 個字面命中，但只有 1 個是真標記，另一個是檔頭註解裡的說明文字。

## B. 分隔空白的量測（決策 1 的依據）

同一段 reset 形狀（一個清單內兩個帶前綴的選擇器），兩種寫法的輸出：

```
現行 placeholder :  …</c:if>input,…</c:if>textarea{color:red}
改用 inline escape:  …</c:if> input,…</c:if> textarea{color:red}
```

* 每一次出現多 1 個空白字元；以 114 次計，全樹多 114 個位元組，集中在 2 個輸出檔。
* **語意相同**：payload 的 EL 字串本來就以空白結尾，所以執行期得到的是兩個空白而不是一個，CSS 等價。
* **宣告層級比對認定相等**：比對器的選擇器正規化會把 `>` 兩側空白收緊，而 payload 結尾正是
  `</c:if>` 的 `>`，於是後面那個空白被正規化掉。實測兩種寫法正規化後字串完全相同。
* **逐 byte 檢查會 FAIL**：這個差異不屬於現有 4 個已核可的序列化分類（結尾分號、小數前導零、
  零值單位、逗號與 `>` 周邊空白），無法解釋的逐 byte 差異會讓檢查把回傳碼設為 1 並印出
  「NO known class explains」。

## C. 三個麻煩處的技術細節

1. **整塊條件**：statement 形式的 escape 在「規則之間」「成對包住規則」兩種位置都已驗證原地存活，
   與現行標記位置一致，預期無額外風險。
2. **taglib header**：現行標記的語意是「header 放這裡」，建置端讀的是來源是否含該標記，
   並據此**跳過**自動前置。改成 escape 後，payload 會是 taglib 指令本身，
   那段判斷邏輯必須改成「是否有一個 escape 帶著 header」，否則兩種錯法都很安靜：前置兩份，或一份都沒有。
   另有一組「不該有 header 的輸出」清單與這段邏輯互動，一併要覆核。
3. **partial 許可**：白名單檢查是在 `@import` 展開之後、用進入點檔名做的，所以 partial 是繼承
   進入點的許可。這也解釋了為什麼 reset partial 帶 placeholder 不會被守門攔下。escape 不需要白名單。

## D. 為什麼不是「順手做掉」

遷移的收益是**減少一套機制**，不是新增能力 —— 使用者要的能力在 escape 上線時就已經有了。
所以它值不值得做，完全取決於 P0 兩個決策的代價；若兩者都選「不擴大公開 API」，
遷移的結果會是「114 份重複 payload + 閘門降級」，那比現狀差。**這是本計畫可能結案為「不執行」的正當理由。**
