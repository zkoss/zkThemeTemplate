# 重算視覺 A/B 覆蓋率(Todo #7 + S30 口徑)

> 計畫檔依 plan mode 規定寫在這裡;**執行時第一步就把它複製到 `tasks/ab-coverage-recount.md`**,
> 依專案慣例(計畫留在 repo 內)。

## Context

**問題**:文件裡現在掛著的 A/B 覆蓋率是 **75/77**(S24,2026-08-05)。那是在 ZK 10.4 補齊
(輸出 77 → **85**)與 P5 之前量的,**分母已經不存在**。S28 曾想順手重算,量出 81/85 後
**自行作廢** —— 探針用「服務出來的尾端 120 字元去彙整檔裡找」,對經過 DSP 求值與 `zk.wcs`
串接的內容不穩定,4 個明明有樣式的檔被判成沒到。

**為什麼要修**:視覺 A/B 是 P4 / P7 收工時唯一的畫面層證據,而它的採信範圍(S33:稀有元件
會真漏接)只能用「85 個輸出檔裡有幾個真的到瀏覽器」來界定。這個數字過期 ⇒ **後面每一次
驗收引用的邊界都是模糊的**。

**探索期新發現(這一條改變了做法)**:4 對舊路徑死複本裡有 **3 對在磁碟上逐 byte 相同**——

| 元件 | 被要求的 | 沒人要的 | 大小 |
|---|---|---|---|
| goldenlayout | `js/zkmax/goldenlayout/css/` | `js/zkmax/layout/css/` | **15864 = 15864** |
| cropper | `js/zkmax/cropper/css/` | `js/zkmax/med/css/` | **4980 = 4980** |
| signature | `js/zkmax/signature/css/` | `js/zkmax/wgt/css/` | **2605 = 2605** |
| tbeditor | `js/zkmax/tbeditor/css/` | `js/zkmax/inp/css/` | 16204 ≠ 15918 |

> **計畫階段這張表的兩欄是寫反的**(原本標成「新路徑 = 分類資料夾」)。實測 + `lang-addon.xml`
> 都指向同一個答案:**活的是元件名資料夾,死的是分類資料夾**。已就地更正。

**任何「拿內容去彙整檔裡找」的探針都分不出這 3 對的哪一邊在彙整檔裡**,兩邊都會判成到了。
S24 只抓到 tbeditor(唯一內容不同的那對)漏掉,**很可能是高報了 3 個**。
⇒ 這次必須用**逐檔唯一的標記**,不是內容比對。

**可證偽的預測**:真值 ≈ **80/85**(85 − 4 個舊路徑死複本 − 1 個桌機 UA 下 `disabled` 的 tablet)。
量到別的數字就是預測錯,**照實記,不調整**。

## 做法

### 1. `scripts/ab-coverage.js`(新檔)+ `npm run visual:coverage`

**為什麼進 repo 而不是一次性腳本**:這個數字已經過期兩次(74/77 → 75/77 → 現在),
而 S28 證明了臨時探針會產出假數字。S30 的紀律是「口徑必須寫下來」——
把口徑寫進一支會自帶斷言的腳本,比寫進一段散文可靠。

流程(單一 JVM、單一次抓取):

1. **快照** —— 讀 85 個 `.css.dsp`,記下每個檔的 sha256 與大小。
2. **注入** —— 每個檔**檔尾**追加一條唯一規則 `\n.zzcov-<nnnn>{--zzcov-<nnnn>:1}\n`。
   - **檔尾安全性已實測**:85 個檔 `<c:if>` 開關全部平衡(0 unbalanced),且全部以 `}` 結尾
     ⇒ 追加點必定在任何 DSP 區塊與 CSS 規則之外。
   - **在 app 啟動之前一次注入全部 85 個** —— 這正好繞開快取風險:`checkPeriod` 未設(= −1)時
     `ExtendletLoader.getLastModified` 回傳常數,`ResourceCache` **不會**因檔案變動而失效,
     所以「邊跑邊改檔」的逐檔探針會靜默服務舊內容。一次注入 = 沒有這個問題。
3. **啟動 + 守門** —— 重用 `ab-visual.js` 的 `startApp()` / `guardProbe()` / `themeFingerprint()`
   (含「Marble `target/classes` 不得上 classpath」那道 `die()`)。
   **這一步已經做掉了**:`scripts/ab-visual.js` 已加 `require.main === module` 護欄 + `module.exports`,
   CLI 行為不變。這是目前磁碟上**唯一**的改動。
4. **抓取** —— GET 頁面 → 解析所有 `<link>` 的 `href`(**含帶 `disabled` 的,標記起來**)→
   逐一 GET → 對取回的 CSS 再跟一層 `@import url(...)`。
5. **判定** —— 每個檔三態:`AGG`(標記出現在彙整 `zk.wcs`)/ `LINK:<名稱>`(出現在另一個
   被連的樣式表,例如 disabled 的 tablet)/ `MISS`(哪裡都沒有)。
6. **還原** —— `finally` 裡從記憶體快照寫回,**逐檔比對 sha256 必須 85/85 相同**,不同就 exit 1。
7. **產出** —— 主控台摘要 + `target/ab-visual/coverage.json`。

### 2. 兩個控制組(不做就不採信數字)

- **正向**:`zul/css/norm.css.dsp` 必須是 `AGG`。它是全樹一定被服務的檔,判成 MISS = 探針壞了。
- **負向**:`--holdout <relpath>` 旗標,故意**不注入**某一個已知 `AGG` 的檔 → 它必須翻成 `MISS`。
  這證明探針讀的是標記,不是記憶。S28 的教訓就是少了這一步。
- **跨頁一致性**:抓兩個不同頁面(`button.zul` 與一個 usecase 頁),標記集合必須相同 ——
  這關掉「一頁就夠」這個至今沒被驗過的假設。

### 3. 要記下來的口徑(S30 的要求)

寫進 `coverage.json` 與文件,缺一項就等於沒記:

| 項目 | 值 |
|---|---|
| 注入什麼 / 注入在哪 | `.zzcov-<nnnn>{--zzcov-<nnnn>:1}`,**檔尾** |
| 比對法 | **精確子字串、區分大小寫**;逐檔唯一 |
| 為什麼免疫於 S30 的兩個歧義 | 標記綁**相對路徑**⇒(a) 不受 `.z-avatar` / `.z-avatargroup` 這類姊妹字首影響;(b) `grid.css.dsp` 三份同名檔(zul / zkmax / zkex)各有各的標記,不會疊加 |
| 抓了哪些 URL | 頁面 HTML 的全部 `<link href>` + 一層 `@import`;**桌機 UA** |
| 位元組口徑 | **磁碟上的 `.css.dsp` 大小**(與 S24 的 35.4% 同口徑,**不是**服務出來的位元組);全樹實測 **640189 B** |

# 實測結果(2026-08-07)

## 一、執行總覽

* **當前狀態:** 成功完成(PASS-WITH-FINDINGS)
* **核心結論:** A/B 覆蓋率上界 = **80/85**,未參與畫面位元組 **6.1%**。
  舊值 **75/77 高報 3 個**,而且這個矛盾從 2026-08-05 起就一直寫在同一份文件裡(S18 vs S24)沒人對過。
* **關鍵產出:** `scripts/ab-coverage.js` + `npm run visual:coverage`、
  `doc/visual-ab-harness.md` §6、閘門紀錄 **#51**、新發現 **S38**。

## 二、完成項目

| 分類 | 檔數 | 說明 |
|---|---|---|
| **到彙整檔**(`zk.wcs`) | **80** | 瀏覽器真的套用 |
| 被連但**不生效** | **1** | `zkmax/css/tablet.css.dsp` —— 200 / 26145 B,但 `<link disabled>`(桌機 UA),P7 的檔 |
| **從來沒有人要** | **4** | `js/zkmax/layout/goldenlayout`、`js/zkmax/med/cropper`、`js/zkmax/wgt/signature`、`js/zkmax/inp/tbeditor` |

**三個控制組全過** —— 正向(`norm` = `AGG`)、負向(`--holdout` 已知 `AGG` 檔 → 翻 `MISS`)、
跨頁(`/button.zul` 與 `/usecase/inventory-table.zul` 命中集合相同)。
**外加一個不必信任程式碼的算術核對**:未注入 551581 B → 注入後 553901 B,
差 2320 B ÷ 每個標記 29 B = **80**,與「80 個檔到彙整檔」逐一相符;負向那一輪 553872 B(少一個標記)。

**閘門與還原**:`check:cssdiff` 跑前跑後都是 **85 / 14863 / 0**;還原 **85/85 sha256** 等於注入前快照。

## 三、發現與數據修正

1. **預測命中,但計畫表的欄位標反了。**
   預測 80/85 成立(85 − 4 死複本 − 1 disabled tablet)。
   計畫階段把「新路徑」寫成分類資料夾(`layout/` / `med/` / `wgt/`),**實際相反** ——
   `<widget-package>zkmax.goldenlayout</widget-package>` 要的是 `js/zkmax/goldenlayout/css/`。
   **活的是元件名資料夾。** 已就地更正,並用 `unzip -p … lang-addon.xml` 獨立印證。

2. **S24 的 75/77 高報 3 個(→ S38)。** 這不是新量測推翻舊量測那麼單純 ——
   **S18 與 S24 本來就互相矛盾**:S18 說「4 個舊路徑從來沒有人要」(宣告層),
   S24 說「只有 1 個舊路徑沒到」(位元組層),兩句不可能同時成立,卻並存了兩天。
   標記探針裁決給 S18。同期真值:74→**71/77**、75→**72/77**。
   **不改 S24 / #38 的既有數字**(附加式紀律),只在 S38 補上高報事實與往後的紀律。

3. **「一頁就夠」這個假設至此才被驗過。** 之前所有覆蓋率量測都只抓一頁,
   而「彙整檔與頁面無關」從來沒有被證明。這次跨頁控制組證實了。

## 四、待決策

**議題:4 個舊路徑死複本要不要刪(77 → 73 的老問題,現在是 85 → 81)**

* **背景:** 這 4 個檔佔 **39367 B / 640189 B = 6.1%**,而且**是本主題目前唯一的未覆蓋來源**。
* **影響:** 不刪 ⇒ 覆蓋率上界永遠停在 80/85,而且每次讀這個數字都要重新解釋那 4 個是什麼。
* **選項:**
  * **【A】留到 P8**(建議)—— L2.5 第 2 項已經掛在那裡,而且它牽涉「上游也該報」的產品面問題。
  * **【B】現在刪** —— 會動輸出檔數 ⇒ G-delta,要重建 `baseline/` 的 manifest。代價不小,收益只是報表好看。
