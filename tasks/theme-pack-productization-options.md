## L1 執行摘要

### 決策前提

#### 一、目標:**隨 ZK EE 附贈,不再獨立販售**

Theme Pack 過去**單獨購買的客戶非常少,收益很低**;多數客戶是**透過客製化做自己公司需要的外觀**。
⇒ ZK 11 起,palette 改為**內含於 EE**(買 ZK EE 就是買 `zkmax.jar`),
讓本來就付費的企業版客戶直接擁有這一套設定集。

**這是目的,不是妥協的副作用。** 後面所有比較都以「哪一種放法最便宜、最不需要新的
產品/模組/授權機制,而且能讓 EE 的價值主張變厚」為尺,**不以獨立營收為尺**。

版本對應(實測 `doc/zk-edition-components.md`):**CE = 無 · PE = `zkex.jar` · EE = `zkmax.jar`**。

#### 二、真正在討論歸屬的不是「CSS 變數」,是兩樣可分離的東西

`--zk-*` 自 **ZK 10.3.0 起就是有文件的公開 API,已出貨 842 個**;本模板主題出貨 **862** 個。
**「客戶能不能自己改配色」兩個大版本前就已經無償開放**,那件事不在討論範圍內。真正要定位的是:

| | 它是什麼 | 可防禦性 | 歸屬 |
|---|---|---|---|
| **(a) 選擇機制** | library property + `ThemeProvider` 追加一張 sheet + `html[data-palette]` 選擇器 + `apply()` | **接近零**(`ThemeProvider` 本來就是公開擴充點) | **EE 啟用**(D1) |
| **(b) 26 組調校過的值** | 623 條宣告 / 108 個 token 名 | 低 | **EE 隨附**(D2) |

⇒ 因為兩者都防不住、也不打算靠它收費,**不必為了保護做任何額外設計**;
既有的版本啟用判斷就綽綽有餘。

#### 三、沒有「維持現狀」這個選項

ZK 11 換預設主題。現行 23 個付費 theme jar 是**舊預設主題的近乎逐 byte 複本**
(實測 `iceblue_c`:81 個可比檔中 79 個逐 byte 相同,282.8 KB 裡 97.5% 是複本)。
母本換掉之後,**這 23 個 jar 不重建就等於報廢**。

⇒ 決策不是「要不要把已有的東西送人」,而是「要不要投入 PA1–PA5 重建它」——
而**附贈給 EE 正是讓這筆投入划算的作法**:同樣的工程量,
產出從「一個賣不動的 SKU」變成「EE 的一項功能」。

#### 四、26 組配色**作為售品**的價值已崩塌,**作為附贈品**的價值仍在

`_amber_css.less` 自己用註解記著 `--zk-color-primary-dark: #D08700; // darken(@colorPrimary, 20%)`,
而 Marble 已驗證的配方可以從**一個 seed** 用 `oklch(from … L calc(c * k) h)` 推出整組協調配色。
⇒ 客戶有一個品牌色就能得到一整組配色,而**多數客戶正是在做這件事**。

**這正是「直接附贈」在商業上正確的原因,而不只是務實妥協。**

> **一個要記著的實測**:**13 / 26 個暗色 palette 依賴 4 個圖檔路徑變數**
> (`@loadingAnimationDefer` 等),那 4 個今天**不是 token**,runtime 換不動
> ⇒ 「26 組資產」並非 26 份等值資產,暗色那半要先補 token 化(機制案 L3.6 第 3 項)。

### 建議

> **主線:A1(隨 EE 附贈,值留在主題 jar、由 EE 啟用)+ E(價值上移到 Theme Builder)。**

| # | 決定 | 建議 | 一句話理由 |
|---|---|---|---|
| **D1** | palette **啟用條件** | **EE**(`WebApps.getEdition()` / `z:getEdition()`) | 目標就是附贈給 EE 客戶;機制案 PA2/PA3 已設計好的閘**原封不動保留** |
| **D2** | **26 組值住在哪個 jar** | **主題 jar 的 `web/zkmax/css/palette/`**,不是 `zkmax.jar` | palette 是**主題專屬資料**(綁該主題的 108 個 token 名);theme-agnostic 的 zkmax 會逼一套 palette 服務所有主題,包含客戶自製主題。**而 tablet 已經是現成的同款先例**(L3.1) |
| **D3** | 要不要開**新 artifact** | **不要** | 為了幾個 API 和一組 CSS 開一個極小專案,pom / release / QA / 授權 / 文件的固定成本與體積不成比例。A1/A2 都不需要 |
| **D4** | **CE/PE 的既有 Theme Pack 買家** | **結轉**:ZK 10.x 授權繼續有效 + 明確告知 ZK 11 起為 EE 功能 + 提供免費 seed 覆寫配方作為替代路徑 | 唯一需要處理的客戶群,**人數極少**(L3.4) |
| **D5** | 投資重心 | 從「維護 26 組配色」移到 **Theme Builder(seed → 配色 + WCAG 驗證 + 暗色推導)** | 對準多數客戶真正在做的事;**與 D1–D4 解耦**,不擋 ZK 11 時程 |

**一句話:**

> **把 26 組配色從「一個賣不動的 SKU」改成「EE 的一行功能清單」是對的;
> 但它們是主題資料,所以應該跟著主題走、由 EE 啟用,而不是搬進 zkmax 的位元組裡。**

## L2 方案逐項評估

### 方案 A 隨 ZK EE 附贈 ★ 建議

**共同優點(A1 / A2 皆有)**:

- ✅ **零新增商業機制** —— 沒有新 artifact、沒有新報價品項、沒有新授權流程。
- ✅ **邊界自動成立且無成本** —— 沒有 EE 就不啟用,不需要發明任何新的保護設計。
- ✅ **EE 的功能清單變厚** —— 「26 組專業配色 + 不必重建 jar 的執行期切換」可以寫進 ZK 11 EE 賣點。
- ✅ **既有 EE 客戶感受最好** —— 升級 ZK 11 白得一項功能;有買 Theme Pack 的 EE 客戶則是無痛延續。
- ✅ **交付物縮到 1/100** —— 每個使用者只下載自己那一張(8–51 條宣告,約 1–2 KB),
  取代 23 個各 ~280 KB 的 jar;**第二份出貨物不存在 ⇒ 不可能再版本漂移**。

---

#### A1 值留在主題 jar,由 EE 啟用 ★

| | |
|---|---|
| **內容** | 26 張 sheet 放在**主題 jar** 的 `web/zkmax/css/palette/`,**只在 EE 下啟用** |

**它不是新設計,是現有模式的複製。** 主題今天**已經**在做一模一樣的事:

```java
// MarbleThemeWebAppInit.java:44-47 —— 現成的先例,一字不用改
String edition = WebApps.getEdition();
if ("EE".equals(edition)) {
    Themes.register(ResponsiveThemeRegistry.TABLET_PREFIX + THEME_NAME, …);
}
```

- **CSS 住在免費主題 jar**:`src/main/resources/web/zkmax/css/tablet/*`(實測存在)。
- **只在 EE 啟用**:非 EE 時那段 `Themes.register` 不執行 ⇒ 樣式永遠不會被載入。
- 主題 jar **已經** import `org.zkoss.zkmax.theme.ResponsiveThemeRegistry`,而且沒有 zkmax 也能正常運作。

⇒ palette 照抄這個模式,得到:

| | |
|---|---|
| ✅ 零新模組、零新 artifact、零新授權機制 | |
| ✅ **palette 跟著主題走** | 每個主題出自己的 palette;客戶自製主題也能出自己的(免費 API) |
| ✅ **機制案 PA1/PA2 幾乎不用改** | `z:getEdition()` 的 DSP 條件、四態測試(含 CE 態)原封不動保留 |
| ✅ build 流程不變 | sheet 與 `zkmax/css/tablet/` 走同一條路 |

**唯一代價**:623 條宣告的位元組會出現在免費 jar 裡,CE 客戶打開 jar 就看得到 hex 值。
**在「不打算靠它收費」的前提下這幾乎沒有成本**:①CSS 本來就防不住(機制案 L3.4(b) 第 2 點)
②客戶用免費的 seed 衍生也能得到等效結果。**它是產品分層標記,不是防拷** —— 見 L3.3。

---

#### A2 值放進 zkmax.jar

| | |
|---|---|
| **內容** | 26 張 sheet + `ThemePalette` API 放進 **zkmax.jar** |

**額外優點**:位元組不出現在免費 jar;連啟用閘都可以不寫(檔案不在 classpath)。

**缺點**:
- ⚠️ **palette 是主題專屬資料,zkmax 是 theme-agnostic 模組** ——
  一套 palette 要服務所有主題,包含**客戶自己做的主題**(而那是多數客戶)。
  客戶的自製主題若沒定義那 108 個 token 名,palette 就是壞的。
  **這不是模組潔癖,是功能正確性問題**(L3.1)。
- ⚠️ zkmax.jar 今天**不含主題 CSS**(慣例是「zkmax 宣告元件、主題提供 CSS」),
  放進去等於新增一個相反方向的依賴。

**判定**:商業上與 A1 等價。**若商務端認為「位元組出現在免費 jar」不可接受,退回 A2**,
並在文件寫明 palette 只保證對官方主題有效。**這是本案唯一需要商務端拍板的取捨。**

---

### 方案 B 獨立付費 artifact

**優點**:商業關係零變動;邊界清楚;交付物大幅縮小。

**缺點**:
- 🔴 **與目標直接衝突** —— 目標是附贈給 EE,不是繼續賣一個賣不動的東西。
- 🔴 **為了幾個 API 和一組 CSS 養一個極小 artifact**,固定成本與體積不成比例。
- ⚠️ 真正的持續成本不是那個 pom,是**契約稅**:108 個 palette token 名要跨每次主題改版保持有效
  (這筆稅在 A1/A2 下**一樣存在**,但至少不必再養一條 release lane)。

**判定**:🔴 不建議。

---

### 方案 C 完全開放給所有版本

**優點**:工程成本低;與 10.3.0 已開放 842 個 token 的決定最一致;
ZK 11 的行銷素材;對多數(自製外觀)客戶最有利。

**缺點**:
- 🔴 **放棄了唯一一項零成本的差異化。** 「附贈給 EE」與「開放給所有人」的**工程成本幾乎相同**
  ⇒ 放在 EE 這一側是**免費得到一項 EE 賣點**,開放則是白白丟掉。
- ⚠️ 不可逆。
- ⚠️ 對既有 Theme Pack 買家的觀感反而比 A 差(付過錢的東西變成人人有)。

**判定**:🔴 不建議 —— 不是因為它壞,而是因為 **A1 用同樣的成本多換到一項 EE 價值**。

> **但要注意分寸**:免費側**必須**保留今天已經有的東西(L3.3 的護欄)。

---

### 方案 D 不做後繼,Theme Pack 隨 ZK 10 終止

基準線。工程成本零,但:
- 🔴 客戶升 ZK 11 就掉外觀,而且是**靜默降級**(機制案 L3.3(b) 紅字:
  `preferred=deepsea` 沒有資源目錄時**不會報錯,只會拿不到樣式**)。
- 🔴 對付費客戶而言,這是**唯一真的「拿走東西」的方案**。
- ⚠️ 「零成本」不完全成立 —— 仍需 PA4 的相容處理或一份明確的 breaking change 公告。

**判定**:🔴 不建議,除非決定完全放棄 palette 這條線。

---

### 方案 E 價值上移:Theme Builder 工具與品牌服務(並行)

palette 一旦變成 EE 的附贈品,它就不再有成長空間,**成長必須來自別處**。
而客戶真正在做的是「用我的品牌色」,不是「從 23 組裡挑一個」—— Theme Pack 從來沒服務到這個需求。

| 交付物 | 內容 | 為什麼客戶付得下去 |
|---|---|---|
| **品牌產生器** | 1 個品牌 seed → 一整份 `:root` 覆寫 sheet(Marble 的 `oklch(from …)` 配方已驗證) | 省掉「調 862 個 token」的體力活 |
| **無障礙驗證** | 對產出配色跑 WCAG AA/AAA 檢查並報告不合格處 | **企業採購的勾選項**,客戶最難自己做對;現行 `wcag` / `wcag_purple` / `wcag_navy` 三件就是這塊價值的證據 |
| **暗色模式推導** | 同一組 seed 推暗色 palette + `color-scheme: dark` | 今天 13 個暗色 palette 靠換圖檔硬幹、runtime 換不動 ⇒ **有真實工程難度** |
| **預覽 / 匯出** | 套在真實元件語料上即時預覽、匯出 drop-in sheet | 降低「改了才知道醜」的風險 |
| **品牌導入服務** | 協助企業識別落地 + 移轉 | 客戶本來就在花這筆錢,只是花在自己的工程師身上 |

**優缺點**:✅ 對準真實需求;✅ 工具與服務**可防禦**(不像 623 條 CSS 宣告);
🔴 是**開新產品**,成本遠高於 A–C。

**判定**:✅ **列為方向,與 D1–D4 解耦。** 先用 A1 把 ZK 11 交代完;
E 另案評估,**最小可行版本是一支 CLI 或一頁靜態產生器**,不必一開始就做成平台。

---

### 方案 F palette 轉為社群內容

把 palette 開源為社群藝廊(Bootswatch 之於 Bootstrap 的模式)。

**判定**:⚠️ **與主線衝突,不建議。** 它與 C 同屬「放棄差異化」那一類;
且常被援引的「免費機制 + 付費內容」成功案例(如 Tailwind UI)賣的是**大量元件與版型**,
不是 22 條宣告 —— **26 組色票不足以獨立支撐一個內容商品**,這也是它該當附贈品的原因。

## L3 附錄

### L3.1 為什麼值應該留在主題 jar

#### (a) 先例已經存在,而且逐項對得上

「EE 專屬的主題樣式」在本專案**不是新模式,是既有慣例**:

| 面向 | tablet(既有,已上線) | palette(照抄) |
|---|---|---|
| CSS 位置 | 主題 jar `web/zkmax/css/tablet/*` | 主題 jar `web/zkmax/css/palette/*` |
| 啟用判斷 | `WebApps.getEdition()` → `"EE".equals(...)`(`MarbleThemeWebAppInit.java:44`) | 同一支,或 DSP 側 `z:getEdition()` |
| 非 EE 時 | `Themes.register` 不執行 ⇒ 樣式永不載入 | sheet 不被追加 ⇒ 樣式永不載入 |
| 對 zkmax 的依賴 | 主題 jar **已經** import `ResponsiveThemeRegistry`,且無 zkmax 時仍正常 | 不需要新增依賴 |
| token 耦合 | `zkmax/css/tablet.css.dsp` 已有 **95 個 `var(--zk-*)`、0 個 hex** | 108 個 token 名 |

⇒ **「由 zkmax 啟用」不等於「必須住在 zkmax.jar」。** 這是本案最容易混淆的一點。

#### (b) palette 是主題專屬資料

- 26 組值綁的是**某一個主題的 108 個 `--zk-*` 名稱**;
- zkmax 是 **theme-agnostic** 的元件模組,它服務所有主題,**包含客戶自製的主題**;
- ⇒ 把 palette 放進 zkmax.jar,等於承諾「這 108 個名字在任何主題下都存在」——
  對**多數客戶(自製外觀)不成立**,palette 在他們的主題下會是壞的或半壞的;
- ⇒ 放在**主題 jar** 裡,這個承諾自動成立(同一份出貨物定義並消費那些名字),
  而且每個主題可以出自己的 palette。

**已有的漂移前科佐證**:機制案 L3.1(c) 量到 **6 個孤兒 token**
(`--zk-primary2`、`--zk-base-border-color-light` 等)—— 主題沒定義、**今天就沒有消費者**。
那正是「palette 與主題分家就會落後」的實證,**跨 jar 只會讓它更容易發生**。

以「EE 加值」為尺(而非獨立 SKU 營收):

| 客戶類型 | 今天 | ZK 11 隨 EE 附贈之後 | 判定 |
|---|---|---|---|

### L3.3 啟用閘的性質與免費側護欄

#### (a) 閘是產品分層標記,不是授權檢查

`WebApps.getFeature("ee")` 底層是 `Classes.existsByThread("org.zkoss.zkmax.Version")` ——
檢查的是 **jar 在不在 classpath**,不是授權有效。ZKMax 自己會驗授權。

> **這一句要寫進決策紀錄**,免得後人以為它是防拷,然後為了「補強」它去加一堆東西。
> **CSS 沒辦法被保護** —— 位元組進了 jar,打開就看得到。這是設計前提,不是缺陷。

#### (b) 免費側的護欄(這條線不能因為 palette 進 EE 而縮回去)

以下**維持免費**,不受本案影響:

| 免費側保留 | 依據 |
|---|---|
| **862 個 `--zk-*` token 可在 `:root` 覆寫** | 10.3.0 起已出貨 842 個的公開 API 承諾 |
| **seed 覆寫配方**(`--zk-color-primary` → 整組衍生) | `../zkThemeTemplate/doc/spec/brand-override.md` |
| **`data-brand` 內建預設集 + `MarbleBrand` 執行期切換器** | 主題既有功能 |

> **口徑**:**EE 拿到的是「26 組調校過的內容」,不是「換色的權利」。**
> 把免費側縮回去,才會變成真正的「拿走東西」。

### L3.4 既有 CE/PE 買家處置

EE 客戶是純加值,沒有處置需求。**只剩 CE/PE 且買過 Theme Pack 的客戶需要配套。**

| # | 動作 | 為什麼 |
|---|---|---|
| **1** | **先盤點名單**(CE/PE + 有效 Theme Pack 授權) | 唯一的風險面,**人數應該極少**;主動接觸的成本遠低於被動處理 |
| **2** | **ZK 10.x 授權繼續有效** —— 現有 jar 不會失效 | 他們沒有失去已買到的東西 |
| **3** | **提供免費替代路徑**:seed 覆寫配方 + 既有 `data-brand` 預設集 | 這條路今天就是免費、有文件、效果等效。對「只是想要某個色系」的客戶就足夠了 |
| **4** | **PA4 的舊 theme name 相容一定要做** —— `org.zkoss.theme.preferred=deepsea` 一個字不用改 | 機制案 L3.3(b):不做就是**靜默降級**,沒有任何錯誤訊息。**所有方案共通、最不能省的一項** |
| **5** | **主動、具名的公告**,綁在 ZK 11 大版本上,框架成「主題能力升級 + EE 加值」 | 大版本是重新定位的正當時機;**靜默地做才是真的會激怒客戶** |
| **6** | 視名單大小提供**升級 EE 的優惠或服務時數** | 人數少 ⇒ 成本極低,而且是一條真實的 EE 升級銷售線索 |

### L3.5 對機制案的具體影響

| **PA5** | migration guide + 零依賴聲明 | 「對模板專案零依賴」聲明**刪除**;改為「**palette 為 EE 功能**」的對外口徑 | 文件 |
