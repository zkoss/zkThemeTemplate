平板層為什麼跟不上

在 zk.xml 設 compact，桌面與平板都會變。用 Java API 在執行期切 compact， 只有桌面會變。2026-08-17 已裁示：這是規格 —— 平板層只認設定值， 因為前一版連建置期以外的切換都沒有。這份文件說明那是什麼情況、平板層本來怎麼蓋過桌面層， 以及四個「把它補起來」的作法各自要付什麼代價（保留備查，不是路線圖）。

現象

同一個 iPad、同一個 compact，兩種設法給你兩種畫面

假設你的系統右上角有一個「舒適 / 緊湊」切換鈕，使用者拿 iPad 開啟，然後按下「緊湊」。 桌面那一層立刻反應：欄位變窄、字變小、列高縮短，而且不用重新整理頁面。 但觸控那一層完全沒動 —— 按鈕、選單、日曆格、調色盤全部維持原來的尺寸。

最好認的例子是調色盤。下面兩個框是真實尺寸，直接照樣式表裡的數字畫出來的：

這裡有個反直覺的地方

平板的 compact 比較大，不是比較小。因為觸控層是「相對於各自桌面基準的補償層」—— 桌面 compact 的底比較小，補償就得推得更用力，才能把觸控目標推回手指點得到的大小。 兩張表追的是大致相同的最終渲染尺寸，只是起點不同。

所以「桌面 compact + 平板 default」不是「小一點的畫面」，是兩層對不上： 底變小了，補償層還照原來的底在補。

原因

樣式表在頁面畫出來之前就選好了，屬性是之後才到的

兩個開關發生在頁面生命週期的不同時刻，這就是全部的原因。

為什麼平板層不能像桌面層一樣「換變數就好」

桌面層的 compact 是純換值：350 個 CSS 變數換一組數字， 瀏覽器當場重算，不用換樣式表。平板層做不到同一件事，這是量出來的：

  • var(--zk- 在平板 default 出現 95 次，在平板 compact 也是 95 次 —— 兩邊一模一樣。
  • 也就是說，變數一點差異都沒承載；差異全在寫死的 px 數字與規則的增減上。
  • 更關鍵的是，有 187 條宣告只存在於 default 那一側（例如 .z-column-content 的 font-size: 15px; padding: 10px 12px，compact 側整條不存在）。它們在 compact 下要的是 不存在，而不是「被換成別的值」。

CSS 沒有「讓這條規則不存在」這種寫法。要讓一段規則消失，只能由伺服器在送出之前把它刪掉 —— 這正是現在的作法，也是為什麼它只能在第 ② 步決定。

現況

四種組合，現在各自拿到什麼

重要的前提

第三列今天本來就是這樣。桌面那一半（D1–D3）完工之後， apply(COMPACT) 就已經是「桌面 compact + 平板 default」了。 這次的改動修好了第二列（以前連 zk.xml 那條路都要換一個 jar 重新編譯）， 沒有把任何一列弄壞。

也就是說：現在討論的不是「新製造出來的缺口」，而是「要不要順便把一個既有缺口一起補掉」。

機制

平板層本來是怎麼蓋過桌面層的？不是靠特異性，是靠排在最後面

量測來源

這一節的數字全部取自 baseline/ —— P0 保存下來的原始建置輸出， 也就是 ZK 用原本的 .less 編出來、未經本案任何改動的那 85 個 .css.dsp。 不是用轉換後的來源量的。（平板那一檔本來就特別乾淨：P4a 的 60 條與 P4b 的 1 條前綴移除 都對它延後、一條沒動。）

一、它是第二個 <link>，而且預設是關的

二、它的選擇器刻意寫得跟桌面層一樣簡單

平板層 359 個單一選擇器的特異性分佈 —— 一半是光禿禿的單一 class， 就是 .z-column-content 這種形狀，跟桌面層那條同名規則完全同級：

三、同級 → 比誰寫在後面 → 平板層贏

CSS 的勝負規則是：先比特異性，一樣才比誰在後面。平板層把自己寫成和桌面層同級， 再靠載入順序拿下。895 條宣告的實際情形：

那 28 個 !important 呢？

平板層確實有 28 個 !important（桌面 84 張表合計 220 個）， 但它們全部集中在 spinner／timebox 的 disabled 狀態， 用途是壓過同一張表裡的 :hover ／ :active。 平板層蓋桌面層，一次 !important 都沒用到。

這個設計的另一面 —— 也就是選項 B 會痛的原因

因為它只贏「平手」，所以只要桌面層那條規則的選擇器比較長，平板層就輸。 全樹有 42 處是這種情形，例如 .z-window-content（平板，0,1,0）輸給 .z-messagebox-window .z-window-content（桌面，0,2,0）。

這不是缺陷，是刻意的。 桌面層那些較長的選擇器描述的是「特殊情境」—— 訊息框裡的視窗、autopaging 的資料列、accordion 的分頁。平板層只想調「一般情況」的觸控尺寸， 沒有理由連特殊情境一起蓋掉。它把自己寫成同級，就是在說「我只贏平手」。

選項 B 加前綴，等於把每一條平板規則從 0,1,0 升到 0,2,1 —— 它就不再只贏平手，也開始贏那些特殊情境。下一節那 16 條就是這麼來的。

選項 B

補的方法：讓每一條平板規則都先問一句「現在是不是 compact」

作法本身很單純 —— 把兩張表都留在瀏覽器裡，各自加一個前綴， 由 <html> 上有沒有那個屬性來決定哪一張生效：

代價

加了前綴，這條規則就開始贏過它本來輸的對手

CSS 決定「同一個屬性誰說了算」的規則是：先比特異性（選擇器裡有幾個 class、幾個標籤名）， 特異性一樣才比誰寫在後面。

平板層今天是靠「寫在最後面」贏的 —— 它的特異性和桌面層一樣低，只是載入順序在後。 一旦加上 html:not([data-density="compact"])，它的特異性就多了一個 class 和一個標籤名， 於是連本來贏不了的桌面規則也一起贏了。

一個具體例子：所有訊息框的內距都會變

這種案例有幾個？量過了：16 個

掃過全部 84 張桌面樣式表，找出「今天靠較高特異性贏過平板規則、加了前綴之後會被反超、 而且兩邊的值真的不一樣」的組合。同一份分析在 baseline/（原始建置輸出）與目前的來源樹上各跑一次，結果完全相同：42 處對決、24 處平板層已用同長度選擇器重述、2 處兩邊同值、16 處會真的改變畫面。

還有一個更硬的選項 A，已經排除

用 :where() 包住前綴可以讓特異性維持不變，上面 16 條就全部消失。 但 :where() 等於把主題的瀏覽器下限拉到 2020 年的 Safari 14 —— 而 L-2 拍板的是「本主題不收窄 ZK 本體的瀏覽器支援範圍」。 更麻煩的是失效方式：舊瀏覽器看不懂這個語法時，是整條規則被丟掉， 不是慢慢降級 —— 舊 iOS 會整層觸控補償直接消失。

選項 C

選項 C：預設那張表一個字都不動，只有 compact 那張加前綴

上一節的痛點是「動到了所有人都在的預設路徑」。那就別動它 —— default 規則維持原樣、繼續靠排在後面蓋桌面層；只給 compact 那張表加前綴， 讓它靠更高的特異性反過來蓋 default 那張。

剩下一：那 187 條漏還在

只有 default 側有、compact 側沒有的 187 條宣告，在 compact 下沒有東西去蓋它們， 會繼續生效 —— 而 iceblue_c 沒有它們。要補，就得把「規則不存在時該有的值」寫進 compact 區塊。 量了一下這件事有多可行：

那 60 條是真正的難處

桌面層在那個選擇器上從來沒宣告過那個屬性，代表「規則不存在時的值」 不是抄來的，是瀏覽器算出來的 —— 來自更短的選擇器、繼承、表格佈局， 或者就是屬性的初始值。實際例子：

  • .z-calendar-cell { width: 36px } —— 桌面層沒有這個寬度，真實寬度是表格佈局算的
  • .ZKBD input[type=checkbox] { width: 24px } —— 不設就是瀏覽器原生尺寸
  • .z-apply-loading-indicator { min-width: 148px } —— 不設就是 auto

這 60 條只能靠瀏覽器實測抓出當下的值再寫死。寫死就會漂移， 而且沒有任何自動化盯著它。這就是「CSS 沒有『這條規則不存在』運算子」的具體長相 —— 你想要的是「width 回到本來就沒有的狀態」，而那沒有寫法。

剩下二：特異性膨脹沒有消失，是換了一側 —— 13 條

前綴把 compact 規則抬到 0,2,1。但在 iceblue_c 裡， 同一條 compact 規則是光禿禿的 0,1,0，本來會輸給桌面層較長的選擇器。 加了前綴就反過來贏 —— 這 13 處會實際改變畫面：

兩者不互斥 —— 值得考慮的混合走法

現行作法與選項 C 可以疊在一起，各管一條路：

  • zk.xml 設定值 → 伺服器只送 compact 那張表， 逐條等於 iceblue_c，這個保證已經證明過，不會動搖。
  • 執行期切換 → 送 default 那張表加上前綴過的 compact 表， 是「盡力而為」的近似 —— 而且可以先補掉最好處理的 126 條（其中 99 條寫 var(--zk-*)，不會漂移）， 把差距壓到剩那 60 條。

代價：行動裝置在沒設定值時要收兩張表（約 53 KB，只有行動裝置付）， 而且文件要誠實寫明兩條路的保證等級不一樣 —— 要和 iceblue_c 完全一致就用設定值，執行期切換是近似。

選項 D

選項 D：不動選擇器，改用 CSS 變數在同一份 DSP 裡切換

前面三個方案都在動選擇器，所以都要付特異性的帳。 如果改成動值呢？兩張表的差異拆成三類，變數對每一類的能耐完全不同：

天花板在哪：變數的「關掉」是 unset，不是「不存在」

把一個 var() 弄成解析不出來，該宣告會變成 IACVT（invalid at computed-value time）， 那個屬性計算成 unset —— 也就是繼承值或初始值。 而「規則不存在」時，值是由層疊裡下一條規則供應的。 這兩件事只有在「沒有下一條規則」時才相同。

但變數有一個很好的變體：把下一條的值寫進 fallback

不要讓它失效，而是讓它掉進 fallback。 --tb-col-fs: initial 會讓 var() 走第二個參數：

選項 D 的真正價值：它不省掉推導，但省掉特異性

那 187 條該寫什麼值，D 和 C 是同一份工作，D 只是換個寫法（fallback 而不是新規則）。 但因為它一個選擇器都沒動，選項 C 那 13 條 compact 側翻盤裡， 有 4 條直接消失（.z-panel-header、.z-paging-icon、 .z-treecell-content 的 padding、.z-notification-content —— 這 4 條兩邊都有，換值就解決）。

剩下 9 條是 compact 專屬的新規則，變數變不出來，只能加規則、只能帶前綴 —— 其中 7 條是 -inplace 輸入元件那一族的 padding。

順帶一提：那個「不存在」運算子其實存在，叫 revert-layer

如果主題有 cascade layer，就有一行解決 187 條的寫法 —— revert-layer 的語意正是「當這條規則不存在，把值退回上一層」：

但它的代價是三個，而且都不小
  • 要對整個主題導入 @layer，不能只給平板層加。 未分層的樣式優先權高於已分層的 —— 只分平板層的話， 84 張未分層的桌面表會反過來蓋掉整個平板層，全毀。 而計畫書 §L2.1 明確把 @layer 列為範圍外： 「會改變 cascade 行為 → 無法用零差異驗證。獨立議題，獨立分支。」
  • 對既有客戶是 cascade 語意變更。 客戶自己寫的未分層 CSS 會贏過所有主題 CSS。多數時候是好事，但那是行為改變，要進遷移指南。
  • 瀏覽器下限 Safari 15.4（2022-03），比 :where() 的 Safari 14（2020-09）還高，而且失效方式更慘： 不認得 @layer 的瀏覽器會丟掉整個區塊 = 整份主題消失。 （另：CleanCSS 5.3.3 會破壞裸的 @layer a, b; 陳述式，本專案已記錄，Marble 有現成的 workaround。）

四個方案的總帳

建議：D 併進 C，不是取代

兩者處理的是不同類型的差異，合起來最省：

  • 187 條只有 default 有的 → 用 D 的 fallback 變數。不動選擇器，99 條寫 token 不會漂移。
  • 75 條兩邊都有值不同的 → 用 D 的純變數換值。免費。
  • 161 條只有 compact 有的 → 只能是新規則，用 C 的 html[data-density="compact"] 前綴。翻盤剩 9 條。

如果日後主題真的走向 @layer（那是獨立議題），那 187 條可以一次全部換成 revert-layer，把推導工作歸零。先做 C+D 不會擋住那條路 —— 屆時是刪掉 fallback、換成一個關鍵字。

裁示

已定案：平板層只支援設定值切換

2026-08-17 裁示 · C24

平板觸控層的密度只由 zk.xml 的 org.zkoss.zul.theme.density 決定。 IceblueDensity.apply() 的兩支方法都不驅動它 —— 這是規格，不是待補的缺口，選項 B / C / D 留作紀錄，不是路線圖。

決定性的理由是：前一版本來就只有這個規格。 @themeProfile 時代要切 compact，作法是「改 LESS 變數 → 重編 jar → 換 jar」—— 平板層從來沒有過任何執行期切換，連整站的都沒有。

這條裁示讓一整批工作消失

前面 B / C / D 三節評估的那 187 條寫回—— 包含 60 條沒有來源可抄、只能實測寫死的—— 全部不必做。它們只在「要讓執行期屬性也驅動平板層」這個前提下才存在。 那三節與它們的實測數字保留在本頁，是為了讓日後若規格真的改變時不必重算， 不是待辦清單。

已經落實的地方
  • 程式碼零改動 —— 目前的實作本來就是這個規格，閘門數字不變，也不需要重跑。
  • IceblueDensity 的 Javadoc 已改寫成規格語氣，並寫明「前一版也沒有」， 讓看 API 的人在那一端就知道，而不是在 iPad 上發現畫面怪怪的才回頭查。
  • D5 的 migration guide 要正面寫這條規格，不要當成注意事項 —— 存量 preferred=iceblue_c 的客戶原本就是換 jar，改設 property 之後行為等價、成本大降； 會期待執行期切換的只有讀了 Java API 文件的新客戶。
